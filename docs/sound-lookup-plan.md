# 音で引く装置 — 設計の記録

2026-08-13 作成。「先人を参照しながら歌詞を書ける仕組み」をどう作るかの検討記録。**数値はすべてこの日時点の実測**であり、カードが増えれば変わる。

Chat からは以下で読める。

```
https://raw.githubusercontent.com/yaoki/lyricstheory-astro/main/docs/sound-lookup-plan.md
```

## 何を作ろうとしているか

やおきさんの言葉をそのまま記す。

> 「りんご」という言葉を引いた時に、他のアーティストがどのような歌詞を書いていて、そこから音声的にどんな構造が読み取れるのかを知りたい

> 私がやりたいのは、単にゼロから歌詞を書くのではなく、**先人を参照できる仕組みづくり**。その時に、**今はみんながなんとなく記憶でやっていることを、辞書を引くようにして書けること**

作詞者のための参照装置であって、研究アーカイブではない。使う瞬間は書いている最中にある。

読む順序も指定されている。**まずどのような文脈でその言葉が使われたかがわかり、次になぜその言葉が使われているかの分析が読める。**やおきさんは音声的な分析から迫る。

## 決まったこと

## 装置が2つ混ざっている

やおきさんの発言には、作り方の異なる2つの装置が同居している。分けないと両方が失敗する。

| | 装置A: 候補生成 | 装置B: 先人参照 |
|:---|:---|:---|
| 引くもの | 語 → 音形 → **別の語** | 語・音 → **観察** |
| 中身 | 語彙辞書（UniDic 等の公開資源） | 分析コーパス（＝ elements のカード） |
| コーパスの壁 | **無い** | ある |
| 空振り | しない（語彙に対して網羅的） | する（17曲しか無い） |
| 使う瞬間 | 書いている最中 | 書く前・書いたあと |

押韻辞典が空振りしないのは、**中身がコーパスではなく語彙辞書だから**にほかならない。「先人の実例」は押韻辞典が持たず、英語圏では Pattison のような教本が別に担っている。執筆時の道具と学習時の教材を1つに負わせると両方落ちる。

装置Aには譜割の注釈も要らない。譜割を決めるのは書いている本人だから、語と読みだけで足りる。

**2026-08-13 時点で着手しているのは装置Bのみ。**装置Aを作るかはまだ決めていない。

## 壁の整理

### コーパス

装置Bを大きくするには全文が要る。ここが国歌大観と決定的に違う——和歌はパブリックドメインなので松下大三郎は本文を持てた。

- **歌詞サイトからの収集は採らない。**サイトの利用規約に反し、CLAUDE.md の「照合の結果を引用の供給に使わない」にも当たる
- **許諾は不可能ではない。**JASRAC は非商用配信の使用料規程を持ち、個人サイトの歌詞掲載は現に許諾で回っていると理解している（未確認。実務を確かめる価値はある）。ただし Public repo に全文を置けない運用は許諾があっても動かないので、結論は変わらない。**変わるのは理由で、「法的に不可能」ではなく「運用方針と費用対効果で選ばない」になる**
- **パブリックドメイン**（唱歌・童謡・民謡）なら合法で、しかも悉皆にできる。ただし「他のアーティスト」の手触りは薄い

### 本当の壁は注釈にある

私的な解析用の複製は日本の著作権法30条の4（情報解析、2018年改正）で扱える範囲にあり、現運用も既に「全文ノートは repo 外」で私的層と公開層を分けている。**取得と保持は壁になっていない。**

壁は、この理論の単位が**譜割シラブル**であることのほうにある。「けい」を `kei` と融合するか `ke`/`i` と割るかはメロディを聴かないと決まらず、CLAUDE.md 自身が「粒度を取り違えると同じ現象が集計上で分裂する」と警告している。合法な全文が1万曲あっても、譜割の注釈は人力で、しかもそれこそがやおきさんの分析行為そのものになる。**注釈の壁は許諾では越えられない。**

### 表示

前後数文字を網羅的に並べると歌詞データベースになる。ただし pivot 図が「字を伏せて位置と粗密だけ見せる」形を実装済みで、これを索引へ広げる道はある。

**ただし動的な索引では破れる。**各クエリがどの位置を光らせるかの合併で、モーラ列全体が復元できてしまう。網羅的な音形索引は、それ自体が本文の復元オラクルとして働く。**抜け道が通じるのは手で作った静的な図までで、動的な KWIC・動的なマスク索引は形式を変えても採らない。**

## 最深部の地雷 — 判定装置への転落

`docs/theory-glossary.md` の冒頭が明言しているとおり、この理論は「XとYで韻が踏める」型の測定ツールではない。ところが「引くと音声的構造が返る」装置は、人手の観察だけを返すのでない限り、定義上の判定機になる。

さらに深い非両立がある。理論の前提は「**同じ音が二度鳴っていても、想起が起きなければ反復ではない**」という位置にある。自動索引が見つけられるのは「同じ音がある」までで、**索引のヒットはこの理論が扱う現象の実例にならない。**実例のように出せば、理論が自分の前提で自分を否定する。「こころ」の裁定——定義を満たすように見えても可否はやおきさんの判断による——が、判断が定義から計算できないことの実例として残っている。

**引ける線は1本。索引の対象を歌詞ではなく観察にする。**

この制約は装置Aにとっては制約にならない。装置Aは「これが反復です」と言わず、音形を共有する語を並べるだけで、想起が起きるかを判定するのは書いている本人になる。**理論が「機械には判定できない」と言っている当の位置に、装置Aは人間を座らせている。**

## Rap Genius との関係

やおきさんは「rap genius とは異なりますが、そのようなイメージ」と述べ、続けて「日本では歌詞の取り締まりも厳しいので rap genius みたいなサイトが望ましいが、非現実的」と結論している。

**非現実的なのは Genius のコピーであって、この庭がやろうとしていることではない。**

Genius が歌詞のライセンスを事業の前提にしているのは、意味の注釈が本文を人質に取るからにほかならない。「この行は○○を指している」は、行そのものが無いと一文字も成立しない。

音韻の注釈は本文を人質に取らない。「カ行の軸がここに散っている」は位置と音だけで成立し、実際に pivot 図がそれで機能している。**制約が重いのは意味の側で、この庭が立っているのは音の側になる。**

同じ形は作れないが、同じ読書体験は作れる。

**ただし1つ、対処の要る衝突がある。**Genius 型は1曲あたりの注釈密度を上げることが成功指標になるので、密度を上げるほど1曲あたりの引用が積み上がる。実測（下記）で涙がキラリ☆は14枚で317字に達している。**1カード1〜2行の制限はカードを守っていて曲を守っていない。**この方向へ進むなら、引用の上限をカード単位から曲単位の予算へ張り替える必要がある。

いまは切迫していない。**張り替えの時機は、P-A の移植で少数の曲にカードが集中的に増え始めたとき。**

## 実測値（2026-08-13、93枚時点）

### 引用の総量

| | 値 |
|:---|---:|
| 異なり引用の総字数（全体） | 2,293字 |
| 涙がキラリ☆（14枚） | 317字 |
| There will be love there（5枚） | 262字 |
| Hello, Again（15枚） | 259字 |
| 口笛（15枚） | 255字 |

### phoneme タグの粒度

`tags.phoneme` は50種、うち23種が1枚のみ。`phoneme × artist` は実在106組・理論上550組で、空欄は80.7%にあたる。

字数で割ると4つの粒度が同居している。

| 字数 | 件数 | 何に付いているか |
|:---|---:|:---|
| 1字 | 98 | pivot 33（子音軸）、V反復 31（母音）、C反復 21（子音）ほか |
| 2字 | 62 | うち CV反復 58（モーラ） |
| 3字 | 8 | syllable 3（正規化ルール7の融合トークン）ほか |

これらは文字列一致しない。`t`（16枚）で引いても `ta`（7枚）のカードは一度も返らない。**空欄80.7%の一部は、未探索ではなく同じ音が粒度で割れているだけ**にあたる。

### カード内の音の共起

カード1枚あたりの音の数は 1個が41枚、2個が33枚、3個が13枚、4個が3枚、5個が2枚。共起する組は80種で、2回以上は16組。上位は `d + t` が9回、`g + k` が4回。

**これは歌詞の性質ではなく、分析の形が出ている。**「た」と「だ」、「か」と「が」が繰り返し同居するのは、清濁を類音として統合する方針（`phoneme-base-voicing-neutral`）がそのまま現れているからにほかならない。観察が返る庭では、共起の網はまず分析者の形をしている。

歌詞の側の隣接データは `figure` の `units`（457枠、隣接する組はおよそ370）が持っている。こちらはカードを1枚書くたびに増える。

## 実装済み — `/elements/sounds/`

装置Bの第一版。93枚に音で引く入口を付けた（commit `7557310`）。

### 申告と到達を分ける

**保存されるタグは分解しない。**融合トークンを `[ke, i]` に割って保存すると「`ke` について観察した」という存在しない申告が登録され、未共起ペアのバックログから本物の未探索が消える（CLAUDE.md の正規化ルール7 が警告している事故）。

代わりにクエリ側へ**片方向の包含**を入れている。

- `t` で引く → `t` のカード（直接）＋ `ta`・`te`・`to` のカード（包含で到達）
- `ta` で引く → `ta` のカードだけ。`t` のカードは「`ta` を観察した」と言っていない

軸に畳むと子音軸18種・母音軸5種になり、t軸は27枚に届く。1枚しか無い軸は生タグの23件から7件へ減る。**93枚のタグは1文字も触っていない。**

実装は `src/lib/phoneme/axis.ts`（分解とかな→ローマ字）と `src/pages/elements/sounds/index.astro`（画面）にある。

### 絞り込みの段

語は複数の軸に分かれるので、どれか1軸で当てると母音「あ」（34枚）のような太い軸が全部を拾う。「りんご」は1軸込みで50枚、2軸以上で10枚。既定を2軸以上にし、内訳（3軸4枚 / 2軸6枚 / 1軸40枚）を出して1軸まで緩める操作を別に置いている。順位は「いくつの軸で当たったか」であって点数ではない。

### URL は1枚だけ

軸ごとの URL は切らない（`docs/network-design-plan.md` の D6）。切った瞬間に軸の綴りが SEO 資産になり、正規化ルールを直したときに301なしで動かせなくなる。絞り込みは `/elements/` と同じくクライアント側が持つ。

`scripts/check-cards.mjs` の検査7（予約語）に `sounds` を足してある。Astro は静的ルートを動的ルートより優先するので、id が `sounds` のカードを書くとビルドは通ったままカードのページだけが黙って消える。

### 既知の欠陥 — ラベルが誤っている

**入力欄の見出しを「語で引く」とし、例に「りんご」を置いたのは誤りにあたる。**

この装置は語を一度も探していない。「りんご」を `ri`・`n`・`go` へ割り、その音を観察したカードを返しているだけになる。最上位に来る口笛の「なら」から「ながら」への展開は、ナ行・ラ行・ガ行を共有するから当たっているのであって、りんごとは何の関係もない。

しかも**「りんご」は93枚の引用に一度も現れない**（2026-08-13 に確認。grep が当たるのは椎名林檎という名前のほう）。歌詞に無い語で引けてしまう画面は、「その語が歌詞にある」と読ませる。

**直すこと**: 見出しを「語の音で引く」に改め、例には分析済みの曲に実際にある語を置く。

## 次にやること・やらないこと

### やること

1. **上記のラベルを直す。**装置が何をしているかを、最初の一瞬で誤解させない
2. **P-A（posfie 楽曲の移植）を進める。**装置Bは中身が増えるほど強くなる。引いて薄かった軸——2026-08-13 時点でワ行2枚、ヤ行1枚、リャ行1枚、撥音1枚——が次の候補になる。`docs/posfie-metrics.md` の優先順と突き合わせる
3. **装置Aを作るか決める。**語彙資源から「語 → C/V骨格 → 同骨格の候補語」を返す装置は、コーパスの壁なしで作れる。判定せず列挙するだけに留める

### やらないこと

- **動的なマスク KWIC**（復元オラクルになる）
- **歌詞の自動走査で「同じ音がある」を実例として出すこと**（判定装置への転落）
- **索引の空振りを「その音が使われていない」と読ませること。**空振りは「まだ書いていない」を意味する

## 未決事項

- **装置Aを作るか。**一次利用者がやおきさん自身と決まったので摩擦は許容できるが、作る判断自体はまだ出ていない
- **既存の韻検索ツールとの差別化を、装置のレベルでどう言うか。**日本語ラップ圏には韻検索ツールが複数ある。既存が引けるのは実質「母音の並びが同じ語」の1軸で、こちらは子音・母音・両方・分布と軸が複数あり、その1つずつに実際の曲の観察が付いている。加えて判定しない。この差を言語化しないと「機能の少ない韻辞典」として受け取られる。用語で Sagishi 氏の指摘を受けて方針を立てたのと同じことを、装置についても要する
- **裸の `n` の衝突。**正規化ルール1 は撥音を `n` と綴るが、実測（93枚）で `n` を持つ3枚はいずれもナ行子音の観察にあたる（`tadashii-machi-n-pivot` の図は「ナ行子音ピボット」）。**撥音だけを観察したカードが書かれた時点で、この2つは衝突する。**そのとき撥音側に別の綴りを与えるか、両方の軸へ載せるかを決める
- **引用の曲単位予算。**張り替える必要は見えているが、時機は P-A で1曲にカードが集中し始めたとき

## 参考にした先行例

- **国歌大観**（松下大三郎・渡辺文雄、1901〜1903）。和歌に通し番号を与え、五句索引——歌の5つの句すべてを音順に並べ、どの句からでも引ける——で本文の側から引けるようにした総索引。**番地と主張を分けている**点がこの構想と重なる——歌に番号を振ったのは索引で、論文は学者が書いた。いまの elements はカードが番地であり同時に主張なので、読みが変わると slug の改名が要る（`tadashii-machi-dashita-tadashi` → `retrograde-dashita` で2世代の301が発生している）
- **押韻辞典**。中身がコーパスではなく語彙辞書であるために空振りしない。装置Aの直接の先行例にあたる
- **歌枕・付合語辞典**。継げるのは検索と教育の機能で、規範の機能は継げない。本歌取りの効果は聴き手の側の共有カノンに依存するが、現代ポップにそれは無い
